# 02. BSDX 武装超过 153 的 exe 补丁位点清单

## 目标

本文的目标是：

1. 记录当前已经确认与否定过的 patch 位点
2. 给出可以直接在 `010 Editor` 里操作的文件偏移
3. 说明这些位点为什么要改，或者为什么暂时不能改
4. 说明 patch 后资产文件是否还要同步改

目标 exe：

- `src/main/resources/ida-reverse/BaldrSky.exe`

所有偏移都基于这份文件。

## 当前最新结论

### 1. “第 154 个武装”正好对应内部索引 `153`

这次实测现象是：

- 武装界面滚轮向下翻
- **正好到第 154 个武装时闪退**

这和反汇编里看到的 `153 / 0x99` 是严格对应的：

- 玩家按 1 开始数
- 程序内部按 0 开始数

所以：

- 第 `154` 个武装
- 就是内部索引 `153`

### 2. 之前扩成 5 处的补丁方向是错的

最初根据字节扫描，额外发现了两处 `push 0x99`：

- `0x455E41`
- `0x456624`

它们一度被加入“第一轮必改”。

但实测结果已经证明：

- 把这两处和原先 3 处一起改掉后
- 游戏一启动就报 `c++ runtime error`

结合反汇编上下文：

- `0x455A60` 周围会加载 `PlugInList.dat / BQPlugInList.dat`
- 这条链更像 PlugIn / ExtraMode 其他子系统
- 不是当前“武装页翻到第 154 个条目才崩”的最短因果链

所以现在的修正结论是：

- `0x455E41`
- `0x456624`

这两处虽然也是 `0x99` 常量，但**当前应排除出第一轮补丁**。

## 第一轮仍可保留的 3 处位点

这 3 处都在：

- `sub_4576F0`

它们位于同一初始化函数里，并且与 `103`、`372` 这种已能和真实资源表规模对上的常量并列出现，因此仍然是第一批最值得保留的容量位点。

### 位点 1

- 反汇编地址：`0x4578BB`
- 文件偏移：`0x56CBB`
- 原始字节：`68 99 00 00 00`
- 建议字节：`68 C8 00 00 00`
- 含义：
  - `push 0x99`
  - 把容量 `153` 传入后续初始化逻辑

### 位点 2

- 反汇编地址：`0x457B51`
- 文件偏移：`0x56F51`
- 原始字节：`68 99 00 00 00`
- 建议字节：`68 C8 00 00 00`
- 含义：
  - `ensureStructArrayCapacity(..., 0x99u, 0)` 前的容量参数

### 位点 3

- 反汇编地址：`0x457BD1`
- 文件偏移：`0x56FD1`
- 原始字节：`68 99 00 00 00`
- 建议字节：`68 C8 00 00 00`
- 含义：
  - 第三组与武装页相关的容量初始化

### 当前测试结论

这 3 处一起改成 `200` 后：

- **仍然不能解决“第 154 个武装闪退”**

所以当前状态不是“补丁完成”，而是：

- 这 3 处大概率仍是相关位点
- 但它们不足以单独解决问题

## 已明确排除的两个位点

下面这两处**不要**再和第一轮武装页补丁一起改：

### 排除位点 A

- 反汇编地址：`0x455E41`
- 文件偏移：`0x55241`
- 原始字节：`68 99 00 00 00`

### 排除位点 B

- 反汇编地址：`0x456624`
- 文件偏移：`0x55A24`
- 原始字节：`68 99 00 00 00`

### 排除原因

1. 它们所在的 `0x455A60` 逻辑会加载：
   - `PlugInList.dat`
   - `BQPlugInList.dat`
2. 这条链在功能上更像 PlugIn / ExtraMode 其他子系统
3. 把它们改成 `200` 后，游戏直接启动失败

所以当前应把它们视为：

- **误命中的同值容量常量**

而不是“武装页专用容量位点”。

## 候选风险点 A：`119`

下面这些位点和分页/页尾上界相关，当前更像第二阶段问题：

### A1

- 地址：`0x79920B`
- 偏移：`0x39860B`
- 原始字节：`C7 44 24 18 77 00 00 00`

### A2

- 地址：`0x7984B3`
- 偏移：`0x3978B3`
- 原始字节：`C7 44 24 10 77 00 00 00`

### A3

- 地址：`0x799738`
- 偏移：`0x398B38`
- 原始字节：`C7 44 24 1C 77 00 00 00`

说明：

- `0x77 = 119`
- 这批位点更像菜单分页上界，而不是当前主崩点

如果将来要尝试把它们抬到 `199`：

- 可原位改成 `C7 00 00 00`

但当前不建议优先动它们。

## 候选风险点 B：`99`

下面这批与：

- `99+`
- `AUTO x`
- `Save100.dat`
- 菜单保护/解锁逻辑

相关。

### 位点

- `0x7A43D4` / `0x3A37D4` / `83 FF 63`
- `0x7A4F52` / `0x3A4352` / `83 F8 63`
- `0x72331D` / `0x32271D` / `83 FE 63`
- `0x7233AB` / `0x3227AB` / `B8 63 00 00 00`
- `0x7A6C35` / `0x3A6035` / `83 FE 63`

### 为什么不能直接把 `63` 改成 `C8`

因为像：

- `83 FF 63`
- `83 F8 63`
- `83 FE 63`

这种是：

- `cmp reg, imm8`

这里的 `imm8` 会做**有符号扩展**。

所以：

- `0x63` 是 `99`
- 但如果你直接把它改成 `0xC8`
- CPU 会把它当成 `-56`

也就是说：

- 这几处**不能**原位单字节改成 200
- 真要改，必须：
  - 改成长指令
  - 或跳到 code cave 重写比较逻辑

所以目前它们只能算：

- 第二阶段候选点

## 不能误改的地方

### `case 153 / 154 / 155`

例如：

- `0x7A5320` 附近 switch 分支里的 `case 153`
- `case 154`
- `case 155`

这些不是容量，而是：

- 菜单命令 ID / 菜单项编号

不能因为数字看着一样就改掉。

## patch 后资产文件要不要改

### 只做这 3 处补丁时

如果你的资产已经有：

- `>153` 武装的 `.mek`
- 以及配套 `waz/spm/grp`

那么：

- **这 3 处补丁本身不要求再额外改资产文件**

因为它们修的是：

- exe 内运行时容量

不是：

- 资产文件协议

### 但如果你的新内容链本身不完整

那当然还是要补齐：

- `.mek`
- 主 `waz`
- 主 `spm`
- `MekaGroup/WazaGroup/SpriteGroup`
- 如有语音/音效，还要 `BatVoice/SeGroup`

这属于新增内容本身的问题，不属于本次 `153` 主崩补丁本身。

## 当前最稳妥的操作顺序

### 第一步

保留当前只改这 3 处的测试版：

- `0x56CBB`
- `0x56F51`
- `0x56FD1`

### 第二步

继续追真正还没挖出来的“第 154 个武装”相关位点，优先方向是：

1. `sub_4576F0` 之外，武装页运行时对象里是否还有别的容量/边界常量
2. `第 154 个武装` 所在页签渲染链里是否有以 `153` 为边界的对象表
3. `721BD0 / 492250 / 7A4200 / 7A5320 / 495D30` 这些函数之间，是否还有未显式写成 `0x99` 的上界

### 当前不要做的事

- 不要再把 `0x455E41`
- `0x456624`

这两处并入测试版

因为已经有实测证据说明：

- 它们会把问题扩大成“启动即 runtime error”

## 当前一句话结论

**“第 154 个武装闪退”这件事已经证明：真正的边界索引就是内部 `153`；但目前已确认的 3 处 `0x99` 位点仍不足以单独修复，而额外补上的 2 处又被实测否定，所以接下来必须继续往武装页运行时链路深挖，而不是继续盲改所有 `0x99`。”**
