# Sou34 Nightmare Party：DX原生局部适配选项（2026-11-10，只读设计）

本轮先读`sou-bats-motion-review-20261106.md`，再核当前Sou定制器、实际BHE/DX原始WAZ、已导出的JSON及现成原生反编译。未实现生产修复，未构建、测试、控制游戏或进程、提交、改共享转换器。按追加授权，仅修正旧审查中距离消费者的错误解释，并生成本报告。缺图片保持nonfatal；静态设计可行不等于实机效果通过。

## 结论与建议选择

存在有真实DX原版技能支持的局部适配路线：把蝙蝠P2改成DX原生的平面追踪root加parent高度追踪，并保留原root距离/攻击条件出口、阶段、攻击、发射数量和散射。它是中心对中心的DX回返近似，不是BHE三维速度与三维转向的严格复现。建议把它作为第一候选，独立完成caller P1的“向原目标突进并减速”，然后以明确实机条件决定是否可交付。

本次最重要的校正是：原P2的ANGLE/OBJECTZ和LENGTH_Z虽然都保存aux `[3,19]`，却不是同一种消费者。ANGLE确实消费root位置加CENTER；LENGTH_Z只用第一个3选root对象，忽略第二个19。BHE和DX的LENGTH_Z都不是XYZ欧氏距离，而是水平欧氏距离加双方中心高度差的绝对值。不存在“必须给距离出口补CENTER”这一要求；应保留该原生公式及root对象。

未找到能在纯DX WAZ中无差异恢复“沿每帧三维目标方向、归一化后乘同一标量并按BHE三维转向限制更新”的现成机制。不要据此宣称数学上绝无其它可能；本轮确认的slot18/19/20/14及条件/位置消费者不提供已证明的等价组合。若必须逐帧等价，需要另外研究引擎级能力，超出此次角色私有图方案。

## 2. 原生消费者的新证据

以下路径均以`src/main/resources/ida-reverse/<engine>/export-for-ai/decompile/`为前缀。

### BHE三维方向与速度

- `bhe/6E9F60.c`读取slot15的XYZ方向，slot23写三维标量并清平面标量；`6EB6F0.c`在三维速度非零时作三维转向；`7355A0.c`经`6F24F0.c`归一化XYZ后乘scalar。
- 蝙蝠P2 slot15的ANGLE/OBJECTZ aux为self `[0,0]` 到root `[3,19]`，有效窗口0～120f及原FF。此处19确是OBJECTPOS2/CENTER。
- caller P1 slot15同为OBJECTZ，但仅15f、目标是 `[1,19]`，即ROCK/当前目标中央。它不是root，也不是HIT或HIT_WAZA。“首击命中”不证明ROCK永远与被命中对象相同；应运行时记录两者身份。
- `bhe/73D890.c`对CENTER按机体状态加height/2或height/4；不能宣称固定一个常数覆盖全部状态。

### DX ANGLE/OBJECTZ不是三维方向

`bsdx/669CD0.c` case2读取两端XYZ后，以`x`和`y-z`投影求单个方向角；`60FCE0.c`、`60A9C0.c`、`5F99E0.c`再按单个角度与平面速度更新向量。因此P2或caller若只补slot18并留下OBJECTZ，目标高度会偏斜水平转向。这一行为与BHE不等价，必须在局部适配中显式改成ANGLE/OBJECT（type1）求XY方向，再独立处理Z。

### 原LENGTH_Z实际是双方中心距离组合

- BHE `71BDE0.c:21～22`调用`73E1E0.c:10～18`，只读取两条aux的第一个整数选择OBJECT。DX `66EA50.c:22～25`调用`668D70.c:10～18`同样如此。二者均不调用CENTER位置锚点函数。
- BHE `71C780.c` case8与DX `66B9C0.c` case7均计算：

`D = round(sqrt(dx*dx + dy*dy)) + abs((selfZ+selfHeight/2) - (rootZ+rootHeight/2))`

- 因此源P2条件aux `[3,19]`的实际目标是root对象，第二个19不参与运算。DX条件宜保留root与25阈值，按当前转换结果守卫；不为了“统一锚点”再增加CENTER、改敌距离或改成仅XY距离。
- 该D不是三维欧氏距离。比如水平20、中心高度差20时，原条件为40，不能因欧氏距离约28.28而替换，更不能误写球形25半径。

### slot20原生中心高度跟随

`bsdx/60FCE0.c:123～175`中，CEventHeight顶层`int1=0`取actor的ROCK；`int1=1`取direct parent。其高度误差为：

`eZ = targetZ + targetHeight/2 - selfHeight/2 - selfZ + heightCorrection`

若水平距离和slot18速度非零，先计算`vZ = eZ * vXY / horizontalDistance`，否则走高度差分支，再应用最大增分及原生越界处理。这个机制追双方中心；不能把它描述成BHE self基点→root CENTER的精确归一化速度。总速度通常为`sqrt(vXY^2+vZ^2)`，并不保持BHE原scalar；方向修正/转弯时也不等价。

该机制的selector不存在root模式。只有确认本私有蝙蝠direct parent就是root才可用int1=1。三等级原图直接发射373为其提供静态基础；仍须核最终重绑图、原生创建身份与实际actor parent/root指针。不要写一个泛化规则把所有direct parent当root。

## 4. 推荐的有界私有图

### 4.1 蝙蝠P2：DX中心回返候选

新增`SouNightmarePartyMotionFixer`（命名建议），按当前Customizer的最后一个角色局部fixer调用。只新增一份私有RESEARCH04四阶段图；三个caller各两条P1发射边共六条改指该副本。原公共源373/目标525及源372/目标524保持原payload；不复制或改动公共整个Tama05文件前缀。

P0/P1/P3、攻击slot41/42、sprite、方向修正16/17、原惯性、原FF、P2条件组合和121f原出口均保留。P2仅明确以下局部差异：

1. slot15从转换后的OBJECTZ改为OBJECT，继续选择root `[3,0]`，保留原窗口和FF，保证只按root XY取方向。
2. 将两条源slot23完整六整数与帧边界重建为本私有P2的DX slot18 type3。不是全局slot23映射；不把已转换DX slot23惯性覆盖掉。
3. 新增P2 0～120f CEventHeight slot20，顶层int1=1。内部slot1为完整恒值最大增分事件，内部相对帧0～120；初始机制参照可采用BLADE的10raw，必须作为未定稿候选值登记。可对其进行有原因的参数调整：例如高度收敛太慢而导致原窗口无法接近root，才提高增分；不能用删高度／改出口来使测试通过。
4. 高度补正为0，使中心高度误差与原LENGTH_Z使用同一root中心。不要为模拟BHE自基点方向随意加selfHeight/2常数，那会重新让速度目标和原中心距离出口不一致。
5. parent失效要有明确退出路径：采用原生OBJECT NULL单独判断，转原P3收尾（suffix INPUT3），排在需要读取parent的条件前。是否在当前原图已有等价失效退出，实施前逐事件核验；新增时作为显式行为设计记录，不以定时器代替。

此候选保留散射、加速/减速、转向扰动和归返攻击特色。它选择DX双方中心对齐作为新契约；这是有边界的改造，不是假称恢复BHE基点/CENTER三维轨迹。尚未实测的最大增分、近垂直路径及root高速移动需要结果决定。

### 4.2 caller P1：独立的取样突进候选

三等级P1在15f只有一次OBJECTZ到ROCK中央的方向取样；15f给64标量，21～28f从先前速度减至0，61f已有jump/gravity归零事件。不要把这一段改成蝙蝠回root，也不要擅自改为HIT_WAZA或最近敌人。

推荐在各caller的独立副本上保留原动作/特效/取消/热量/出口，只修改P1运动：

- 15f方向改为ANGLE/OBJECT到原ROCK，保留单帧取样，不延长为0～102f连续锁定。
- 完整重建源两条速度事件为局部slot18，保留15f与21～28f、所有六整数。这样恢复短促水平突进和减速。
- 为恢复空中目标可达性，15f单次加入slot20 int1=0（原caller本来就是ROCK目标，因此这里没有新增敌人改绑）；高度补正0，按双方中心计算一次vZ。它必须与15f取样的同一个ROCK对象对应。蝙蝠slot20仍必须是int1=1，两者测试应交叉拒绝。
- 21～28f向slot19补“从已有jump速度减到0”的`[1,0,0,0,0,0]`，保留原61f事件。否则15f高度速度会在水平停止后继续积累高度。
- slot20最大增分不能照搬回返10raw，否则单帧突进几乎不升高。可先用6400raw（每帧最大速度增量64）作为明确有界的试验候选，结合P0已归零jump的前提验证；它不是最终平衡结论。对水平距趋零且高度很大的情形，原生分支可能得到大vZ或裁剪差异，必须测量实际速度上限和收尾，不依据同名字段推断无问题。

上面的caller方案是“原ROCK方向的单次取样突进＋单次中心高度补偿＋同步减速”。不同于持续追尾，最接近原15f只取样一次的意图，但其水平64而非三维总速64、self中心而非self基点的差异必须明示。若实测升降突兀，可在同一15～28f运动窗口内调整水平速度和高度最大增分；不得扩大原锁定窗口、强制命中或删除首击条件来掩盖效果问题。

caller不必添加新玩家武装或MEK条目。可以深复制三个原caller后在当前Sou WAZ中原索引事务替换，其他引用保持；与仅追加公共蝙蝠的策略一起，避免为主招引入不必要的新技能编号。若采用私有main尾部追加，则必须同步全部原main入口映射与条件ACTION_WAZA，成本更高，本问题没有已证明需要。

### 4.3 不推荐作为第一实现的路线

- slot18加固定slot19：没有根据实时root/目标高度计算，任意高低差下不成立。
- P2保留OBJECTZ只补slot18：高度会污染XY方向。
- P2 slot20 int1=0：追原敌目标，与root回返身份冲突。
- 用LENGTH或独立高度阈值替代原LENGTH_Z：改变原出口，且本次已确认没有必要。
- slot14 CEventMove：`64D6D0/64D780`确实可以在XYZ端点之间插值，结束端点可更新；但未找到原版实例、没有CENTER扩展、时间参数替代了速度/转向，且坐标设置参与阶段与碰撞的顺序需要额外验证。它可以成为“按时收束”的重新设计研究，不能当作速度等价恢复或靠固定时间回收过关。
- 修改Sou公共SPM发射矩形为CENTER：牵涉所有动画帧、其它武器与姿态；当前native中心对齐路线无需扩大到该范围。
- slot44“パラメータ変動”：实际是CEventStatus，维护属性状态而非任意XYZ赋值表达式，不是通用算式槽。

## 5. 按现有fixer模式落实的边界

`SouCustomizer.java`当前调用SkillGlitch、HumanCannon、CursedBlade、SnowMoon、FlareSeeker、CoolGain、BoostProcter。`SouCoolGainReturnProtocolFixer.java`提供最接近的完整守卫模型：actual common append plan解析host/source slice；双名定位；原记录字节签名；按当前映射独立重编译；期望图与实际图比较；所有候选构造和检查通过后再发布host/main/GRP共享视图。

建议沿这个模式做单一角色fixer：

- 从raw sou与raw common tama05建立四个必需源身份，524可作为只读首击控制守卫；不硬编码host skill525、host group或尾部索引。
- 私有蝙蝠只能追加在登记的source slice之外、当前host动态尾部；日英私有名必须都唯一。原图/主图/MEK/WazaGroup计数不一致则拒绝。
- 单一完整安装态包含“一份私有蝙蝠＋六条caller边＋三个caller运动图”。不能识别到私有名后只检查名称就当幂等；任何caller只装一半、任一边仍指公共体、重复私有名、移动事件/出口漂移均拒绝。
- 再运行不追加且零payload变化；允许后续其它合法私有图继续追加，不能要求自己永远占据最后一项。
- caller只保留预先列出的控制/运动与六条引用差异。其余动作、伤害、等级数量、SPM/SE/voice、热量、取消、原结束条件逐项保全。公共525不得被后来私有改写反向污染。

- 不改followup/tsukuyomi全局23→-1，不扩大到其它角色、其它BHE三维速度或默认敌目标规则。

## 6. 有意义的回归与运行证据

静态与二进制回归应包括：

1. 从当前真实BHE二进制解析三等级和源373，逐一验证完整签名、phase/suffix、两个速度事件、source double-name以及三等级六条直发边；核当前转换公共图与独立预期一致。
