# Vanilla 保存菜单标题编码取证（2026-10-27）

## 结论

运行时出现的 `A1 BA BF CB C0 EF CB B9 A1 BB 20 BD E1 CA F8 00` 已在 vanilla 隔离运行所用的旧存档副本 `Save002.dat` 中精确定位：它位于第一个 zlib 块解压后的 `0xF300`，严格按 CP936 解码为 `『克里斯』 结束\0`，重新编码后逐字节一致。该位置正好是保存菜单从存档头取标题的字段。

这条字符串无需假设由本轮移植包引入。`Save002.dat` 当前 SHA-256 与隔离运行创建时记录的用户原存档 seed SHA-256 相同；vanilla 本身继承了该存档。随后检查的 26 个保存菜单标题均严格按 CP936 往返并显示完整中文，已有明确语义映射的独立 CP932 兼容种子见后文。这里确认的是这些标题字段，不能据此把原版资源、全部存档内容或整个资源树标为 CP936。

## 存档到标题显示的读取链

以下依据为 `src/main/resources/ida-reverse/bsdx/export-for-ai/decompile/` 的现有反编译导出。反编译器对隐含 `this` 的展示并不一致；结合被调函数读取 `CFile` 及参数用途判断，不把某一处伪 C 调用的参数个数当作真实 ABI。

1. `721BD0.c:38` 按 `%sSave\\Save%03d.dat` 打开 `a1+1` 对应的存档；第 89–94 行检查前两个 DWORD 为 100、863596，再把大小 63336 的第一块解压到调用者给定地址。
2. `76CC20.c:17` 读取解压大小，第 24–27 行读取压缩大小和数据，第 32 行交给 `693730`。`693730.c:28` 初始化 zlib `1.2.1` 的 inflate 流，第 31–35 行以结束模式解压。这与文件上的 `78 9C`、完整校验和及解压大小一致。
3. `492250.c:1280` 把目标地址设为 `this + 368`。同一函数多处创建 `SaveMenuNo`，第 1402 行读取 `SaveChapterLogo.spm`，并含 `NO DATA`／版本检查路径，因此这里是保存菜单头信息读取，不是仅凭文件名猜测的 replay 路径。
4. `492250.c:1655–1658` 从 `this + 62576` 读取 NUL 终止字符串，用 `strlen` 的 15 字节长度构造字符串，再送入 `454070` 的多字节文字处理。
5. 两个地址相减：`62576 - 368 = 62208 = 0xF300`。这与 `Save002.dat` 解压头中的精确命中位置相同，不仅是整文件中偶然存在相同文字。

因此可复核的数据流是：

```text
Save002.dat first zlib block at file +0x10
  -> 63336-byte decoded header at menu object +368
  -> header +0xF300 == menu object +62576
  -> strlen == 15, then 454070
```

`721BD0.c`、`76CC20.c`、`693730.c` 已完整读取；`492250.c` 是针对上述菜单入口和标题消费位置的定点阅读，不宣称完整审计其 1737 行。
